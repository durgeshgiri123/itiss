# SESSION 1 & 2: COMPLIANCE AUDIT FUNDAMENTALS

---

## 1.1 What is a Compliance Audit?

A **systematic, independent evaluation** of an organization's adherence to:

| Category | Examples |
|---|---|
| **Regulatory Requirements** | Laws, statutes, government mandates |
| **Internal Policies** | Company rules, SOPs, codes of conduct |
| **Industry Standards** | ISO, NIST, PCI-DSS, COBIT |
| **Contractual Obligations** | Client contracts, vendor agreements |

---

## 1.2 Primary Goals (Why Conduct Audits?)

| Goal | Explanation |
|---|---|
| **Ensure Adherence** | Verify compliance with laws, regulations, policies, and standards |
| **Risk Reduction** | Identify gaps before they become breaches, fines, or lawsuits |
| **Improve Security** | Strengthen controls across people, process, and technology |
| **Maintain Credibility** | Build trust with clients, regulators, partners, and the public |
| **Mitigate Fines** | Avoid monetary penalties, sanctions, and legal liability |
| **Ensure Smooth Operations** | Continuous, sustainable, and disruption-free business processes |

---

## 1.3 Memory Aid: The "C.R.I.M.E." Pillars

- **C**redibility — trust and reputation
- **R**isk Mitigation — identify and reduce risk
- **I**ntegrity — ethical operations
- **M**onetary Penalties — avoid fines
- **E**fficiency — smooth, sustainable operations

---

## 1.4 Cybersecurity Challenges for Organizations (6 Key Challenges)

| # | Challenge | Detail |
|---|---|---|
| 1 | **Evolving Threat Landscape** | Ransomware, phishing, APTs — threats constantly mutate |
| 2 | **Complex IT Environments** | Hybrid cloud, IoT, remote work — expanded attack surface |
| 3 | **Regulatory Pressure** | Must comply with GDPR, HIPAA, PCI-DSS simultaneously |
| 4 | **Resource Constraints** | Limited budgets and shortage of skilled cybersecurity personnel |
| 5 | **Third-party Risks** | Vendors/partners introduce vulnerabilities into the supply chain |
| 6 | **Data Privacy** | Protecting sensitive data amid rising breach incidents |

---

## 1.5 Compliance Basics

**Compliance** = Adhering to laws, regulations, guidelines, and specifications relevant to an organization.

### Three Key Components:

1. **Regulatory Frameworks** — external laws and mandates (GDPR, HIPAA, SOX, PCI-DSS)
2. **Internal Policies** — company-specific rules, codes of conduct, procedures
3. **Industry-Specific Standards** — sector-based guidelines (ISO, NIST, COBIT)

---

## 1.6 Types of Security Audits (5 Types)

| Type | Conducted By | Purpose |
|---|---|---|
| **1. Internal Audit** | In-house audit team | Identify gaps before external scrutiny; self-assessment |
| **2. External Audit** | Independent third-party | Objective evaluation; often required for certification |
| **3. Regulatory Audit** | Government/regulatory body | Enforce legal compliance (SEBI, RBI, GDPR enforcers) |
| **4. Certification Audit** | Accredited certification body | Verify compliance with specific standards like ISO 27001 |
| **5. VAPT** | Security testers/ethical hackers | Identify and address technical vulnerabilities (penetration testing + vulnerability scanning) |

---

## 1.7 Audit Decision Factors (5 Factors)

| Factor | Key Question |
|---|---|
| **Scope** | What areas, systems, or processes will be audited? |
| **Frequency** | How often should audits be performed? (Annual, quarterly, continuous) |
| **Resources** | Availability of tools, skilled personnel, and budget? |
| **Compliance Mandates** | What regulatory/industry requirements are driving the audit? |
| **Risks** | Which high-risk areas or processes should be prioritized? |

---

## 1.8 Security Audit Phases (4 Phases)

```
┌──────────────┐    ┌──────────────┐    ┌──────────────┐    ┌──────────────┐
│ 1. PREPARE   │ -> │ 2. EXECUTE   │ -> │ 3. REPORT    │ -> │ 4. FOLLOW-UP │
└──────────────┘    └──────────────┘    └──────────────┘    └──────────────┘
```

| **2. Execution** | Gather evidence; conduct interviews; evaluate controls; test samples |
| **3. Reporting** | Document findings; provide recommendations; issue formal audit report |
| **4. Follow-up** | Verify corrective actions; track remediation; close audit gaps |

---

## 1.12 Key Audit Terminology

| Term | Definition |
|---|---|
| **Audit Criteria** | The "benchmark" — policies, standards, regulations against which conformance is measured |
| **Audit Evidence** | Verifiable records, statements of fact, or information supporting conclusions |
| **Non-conformity (NC)** | Failure to meet a specified requirement |
| **Major NC** | Significant failure affecting the management system's integrity |
| **Minor NC** | Isolated lapse; does not compromise the entire system |
| **Observation / OFI** | Opportunity for Improvement — not a failure, but a suggestion |
| **Corrective Action** | Action to eliminate the root cause of a detected non-conformity |
| **Preventive Action** | Action to eliminate the cause of a potential non-conformity |
| **Audit Trail** | Chronological record of audit evidence, activities, and decisions |
| **Materiality** | Significance of a finding; would it influence stakeholder decisions? |
| **Sampling** | Selecting a representative subset of data/transactions for testing |
| **Walkthrough** | Tracing a transaction/process end-to-end to understand controls |
| **Substantive Testing** | Detailed testing of transactions/balances to detect material errors |

# SESSION 3: SECURITY EVALUATION

---

## 2.1 What is Security Evaluation?

A **systematic assessment** of an organization's security posture against established standards and threats.

### Objectives:
- Identify vulnerabilities
- Assess effectiveness of controls
- Measure security posture against benchmarks

---

## 2.2 Evaluation Process (4 Steps)

```
┌──────────────────┐    ┌──────────────────┐    ┌──────────────────┐    ┌──────────────────┐
│ 1. Define         │ -> │ 2. Data          │ -> │ 3. Analysis      │ -> │ 4. Report        │
│    Objectives     │    │    Collection     │    │                  │    │    Findings      │
└──────────────────┘    └──────────────────┘    └──────────────────┘    └──────────────────┘
```

| Step | Activity |
|---|---|
| **1. Define Objectives** | Determine what needs evaluation and why |
| **2. Data Collection** | Gather data through logs, interviews, system reviews |
| **3. Analysis** | Compare data against benchmarks and standards |
| **4. Report Findings** | Summarize strengths, weaknesses, and recommendations |

---

## 2.3 Evaluation Phases (5 Phases)

| Phase | Activity |
|---|---|
| **1. Planning** | Establish scope, goals, and evaluation criteria |
| **2. Assessment** | Conduct reviews, tests, and interviews |
| **3. Analysis** | Identify gaps and prioritize risks |
| **4. Remediation** | Develop and execute a plan to address findings |
| **5. Monitoring** | Track improvements; ensure ongoing compliance |

---

## 2.4 Assurance — The 7 Evaluation Levels (Increasing Confidence)

| Level | Name | Description |
|---|---|---|
| **EAL 1** | Functional Testing | Basic testing; confidence in correct operation |
| **EAL 2** | Structural Testing | Design-level testing with developer cooperation |
| **EAL 3** | Methodical Design and Testing | Systematic testing from design phase onward |
| **EAL 4** | Methodical Design, Testing, and Review | More rigorous review and independent verification |
| **EAL 5** | Semiformally Designed and Tested | Semi-formal models; resistance to moderate attacks |
| **EAL 6** | Semiformally Verified Design and Tested | Formal verification of high-level design |
| **EAL 7** | Formally Verified Design and Tested | Full formal verification; highest assurance level |

> **Note:** These map to Common Criteria (ISO/IEC 15408) Evaluation Assurance Levels (EAL 1–7).

---

## 2.5 Evaluation Methodology (3 Pillars)

| Pillar | Detail |
|---|---|
| **Standards** | Use established frameworks like ISO/IEC 15408 (Common Criteria) |
| **Techniques** | Code reviews, penetration testing, risk analysis, threat modeling |
| **Tools** | Automated vulnerability scanners, SIEM, log analysis, monitoring tools |

# SESSION 4: NIST FRAMEWORK

---

## 3.1 NIST Overview

- **National Institute of Standards and Technology** (US government agency)
- Provides guidelines and standards to strengthen cybersecurity
- **NIST Cybersecurity Framework (CSF)** is the most widely adopted framework

---

## 3.2 NIST CSF — 3 Components

### (A) Core — 5 Functions

```
┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐
│ IDENTIFY │ → │ PROTECT  │ → │ DETECT   │ → │ RESPOND  │ → │ RECOVER  │
└──────────┘   └──────────┘   └──────────┘   └──────────┘   └──────────┘
```

| Function | Purpose | Examples |
|---|---|---|
| **IDENTIFY** | Understand business context & risks | Asset inventory, risk assessment, governance |
| **PROTECT** | Implement safeguards | Access control, training, encryption, maintenance |
| **DETECT** | Discover cybersecurity events | Monitoring, anomaly detection, continuous surveillance |
| **RESPOND** | Take action on detected events | Response planning, communications, analysis, mitigation |
| **RECOVER** | Restore capabilities/services | Recovery planning, improvements, communications |

### (B) Implementation Tiers (4 Tiers)

| Tier | Name | Description |
|---|---|---|
| **Tier 1** | Partial | Ad-hoc, reactive; risk management not formalized |
| **Tier 2** | Risk-Informed | Risk management approved but not organization-wide |
| **Tier 3** | Repeatable | Formal, organization-wide risk management policy |
| **Tier 4** | Adaptive | Proactive; adapts based on lessons learned and threat intelligence |

### (C) Profiles

- **Customized cybersecurity outcomes** tailored to organizational needs
- Aligns framework functions/categories with business requirements, risk tolerance, and resources
- **Current Profile** vs. **Target Profile** — gap analysis drives roadmap

---

## 3.3 Uses of the NIST Framework

| Use Case | Description |
|---|---|
| **Align Cybersecurity with Business** | Bridge gap between tech and business objectives |
| **Assess & Improve Security Posture** | Baseline measurement and continuous improvement |
| **Foster Communication** | Common language for technical and non-technical stakeholders |
| **Prioritize Investments** | Risk-based budgeting for cybersecurity initiatives |

# SESSION 5: GDPR COMPLIANCE

---

## 4.1 GDPR Overview

- **General Data Protection Regulation** (EU, effective May 25, 2018)
- Protects privacy and personal data of **EU citizens**
- Applies to **any organization worldwide** that processes EU citizen data (extraterritorial scope)
- Penalties: Up to **€20 million or 4% of annual global turnover**, whichever is higher

---

## 4.2 Types of Privacy Data Protected by GDPR

| Category | Examples |
|---|---|
| **Personal Identifiable Information (PII)** | Name, address, phone, email, ID numbers |
| **Sensitive Data (Special Categories)** | Health records, biometric data, genetic data, political opinions, religious beliefs, financial data |
| **Behavioral Data** | Web browsing activity, preferences, location data, cookies, IP addresses |

---

## 4.3 GDPR — 7 Key Steps to Ensure Compliance

| # | Step | Description |
|---|---|---|
| 1 | **Data Inventory** | Identify and document all personal data processed (data mapping) |
| 2 | **Legal Basis** | Ensure lawful basis for collection (consent, contract, legal obligation, legitimate interest, vital interest, public task) |
| 3 | **Privacy Policies** | Create transparent, clear, accessible privacy notices |
| 4 | **Data Subject Rights** | Enable: access, rectification, erasure (right to be forgotten), portability, restriction, objection, automated decision-making |
| 5 | **Breach Management** | Detect, investigate, and report breaches within 72 hours to supervisory authority |
| 6 | **Data Protection Officer (DPO)** | Appoint DPO when required (public authorities, large-scale processing, special categories) |
| 7 | **Regular Audits** | Conduct compliance checks; update processes; maintain records of processing activities (ROPA) |

---

## 4.4 Key GDPR Principles (Article 5)

| Principle | Meaning |
|---|---|
| **Lawfulness, Fairness & Transparency** | Process data legally and be open about it |
| **Purpose Limitation** | Collect for specified, explicit, legitimate purposes only |
| **Data Minimization** | Collect only what is necessary |
| **Accuracy** | Keep data accurate and up to date |
| **Storage Limitation** | Keep data no longer than necessary |
| **Integrity & Confidentiality** | Ensure appropriate security |
| **Accountability** | Controller is responsible for demonstrating compliance |

# SESSION 6 & 7: ISO STANDARDS (ISO 27000 Family)

---

## 5.1 ISO 2700x Family Overview

- **International Organization for Standardization (ISO)** — global standards body
- **ISO 2700x** = Family of standards for **Information Security Management**
- Core focus: Protect **Confidentiality, Integrity, and Availability (CIA)** of information
- **ISO/IEC 27001** = The most well-known standard; specifies requirements for an **Information Security Management System (ISMS)**

### Key Standards in the Family:

| Standard | Purpose |
|---|---|
| **ISO 27000** | Overview and vocabulary |
| **ISO 27001** | ISMS requirements (certifiable standard) |
| **ISO 27002** | Code of practice for information security controls |
| **ISO 27005** | Information security risk management |
| **ISO 27017** | Cloud security |
| **ISO 27018** | Protection of PII in public cloud |
| **ISO 27701** | Privacy Information Management (extension to 27001) |

---

## 5.2 How the Standard Works

1. Organization adopts ISO 27001 to **systematically manage sensitive data**
2. Includes: risk assessments → control selection/implementation → continuous monitoring
3. **Certification** demonstrates compliance to stakeholders and regulatory bodies

---

## 5.3 History of ISO/IEC 27001

| Year | Milestone |
|---|---|
| **1990s** | Originated from British Standard **BS 7799** |
| **2005** | ISO adopted and published as **ISO/IEC 27001:2005** |
| **2013** | Major revision — restructured using Annex SL; aligned with other ISO management standards |
| **2022** | Updated with new controls (2022 version) — 93 controls across 4 themes |

---

## 5.4 ISO/IEC 27001:2005 — 11 Domains (Original Structure)

| Domain # | Domain Name | Key Focus |
|---|---|---|
| 1 | **Security Policy** | Information security policy document; management commitment |
| 2 | **Organization of Information Security** | Internal organization; mobile devices; teleworking |
| 3 | **Asset Management** | Asset inventory; classification; handling |
| 4 | **Human Resource Security** | Screening; employment terms; training; discipline; termination |
| 5 | **Physical and Environmental Security** | Secure areas; equipment security; clear desk/screen |
| 6 | **Communications and Operations Management** | Network management; media handling; malware protection |
| 7 | **Access Control** | Access control policy; user management; system access |
| 8 | **Information Systems Acquisition, Development, and Maintenance** | Security in SDLC; test data protection |
| 9 | **Information Security Incident Management** | Incident reporting; response; lessons learned |
| 10 | **Business Continuity Management** | BCP; DRP; redundancy |
| 11 | **Compliance** | Legal requirements; standards compliance; audit |

> **Note:** 2013 revision restructured to Annex SL (Clauses 4–10); 2022 version further reorganized controls.

---

## 5.5 Structure of ISO Standards — PDCA Cycle

```
      ┌──────────────────────────────────────────┐
      │              PLAN                         │
      │  Establish ISMS objectives, policies,     │
      │  scope, risk assessment methodology       │
      └──────────────────┬───────────────────────┘
                         │
      ┌──────────────────▼───────────────────────┐
      │              DO                           │

                         │
      ┌──────────────────▼───────────────────────┐
      │              CHECK                        │

      └──────────────────┬───────────────────────┘
                         │
      ┌──────────────────▼───────────────────────┐
      │              ACT                          │
      │  Improve and update the system;           │
      │  corrective & preventive actions          │
      └──────────────────────────────────────────┘
```

---

## 5.6 Annex A

- Provides a **comprehensive list of controls** (reference control objectives and controls)
- ISO 27001:2013 — Annex A had **114 controls in 14 domains**
- ISO 27001:2022 — Annex A restructured to **93 controls in 4 themes**:
  1. Organizational controls
  2. People controls
  3. Physical controls
  4. Technological controls

---

## 5.7 ISMS Key Elements

| Element | Description |

# SESSION 8: SOX AND SOC REPORTS

---

## 6.1 SOX (Sarbanes-Oxley Act) Reports

### SOX Overview:
- Enacted in **2002** (USA) after Enron/WorldCom scandals
- Designed to **prevent corporate fraud** and **improve financial transparency**
- Applies to **all publicly traded companies** in the U.S.

### Key Sections:

| Section | Name | Requirement |
|---|---|---|
| **Section 302** | Corporate Responsibility | CEO/CFO must personally certify financial reports (& internal controls) |
| **Section 404** | Internal Control Assessment | Management must assess and report on effectiveness of internal controls over financial reporting (ICFR); external auditor must attest |

### SOX Compliance and Security Controls:

| Control Area | Details |
|---|---|
| **Access Management** | Segregation of duties; least privilege; periodic access reviews |
| **Change Management** | Controlled changes to financial systems; approval workflows |
| **Incident Response** | Detect and respond to incidents affecting financial data |
| **Backup & Recovery** | Ensure availability and integrity of financial records |
| **Audit Trails/Logging** | Maintain logs of all financial transactions and system access |

---

## 6.2 SOC Reports (System and Organization Controls)

### Three Types of SOC Reports:

| Report Type | Focus | Audience |
|---|---|---|
| **SOC 1** | Internal controls over **financial reporting** (ICFR) | User auditors and management |
| **SOC 2** | Controls over **security, availability, processing integrity, confidentiality, and privacy** (Trust Services Criteria) | Management, regulators, customers |
| **SOC 3** | Publicly available **summary** of SOC 2 findings (no detailed controls) | General public; marketing purposes |

### SOC — Types of Reports:

| Type | Description |
|---|---|
| **Type I** | Design of controls at a **point in time** |
| **Type II** | Design AND **operating effectiveness** over a period (typically 6–12 months) |

### SOC 2 Trust Services Criteria (5 Criteria):

| Criterion | Focus |
|---|---|
| **Security** | Protection against unauthorized access |
| **Availability** | System is available for operation and use |
| **Processing Integrity** | System processing is complete, valid, accurate, timely, and authorized |
| **Confidentiality** | Information designated as confidential is protected |
| **Privacy** | Personal information is collected, used, retained, disclosed, and disposed appropriately |

### Auditor Process Overview (SOC):

1. **Risk Assessment** — identify key risks and controls
2. **Evidence Collection** — test design and operating effectiveness
3. **Reporting** — issue SOC report with auditor's opinion

# SESSION 9: COBIT FRAMEWORK

---

## 7.1 COBIT Overview

- **Control Objectives for Information and Related Technologies**
- Published by **ISACA**
- A framework for **IT governance and management**
- Goal: **Align IT processes with business goals**

### COBIT Principles:

| Principle | Description |
|---|---|
| **Meeting Stakeholder Needs** | IT delivers value to stakeholders |
| **Covering the Enterprise End-to-End** | Holistic; includes all IT and business functions |
| **Applying a Single Integrated Framework** | Integrates with other standards (ITIL, ISO, NIST) |
| **Enabling a Holistic Approach** | Considers processes, structures, culture, information |
| **Separating Governance from Management** | Governance = evaluate, direct, monitor; Management = plan, build, run, monitor |

---

## 7.2 COBIT Components (5 Components)

| Component | Description |
|---|---|
| **1. Framework Core** | Principles, policies, and governance framework |
| **2. Processes** | Governance and management objectives (40 processes in COBIT 2019) |
| **3. Organizational Structures** | Roles, responsibilities, committees, decision rights |
| **4. Information** | Data governance; information flows and quality |
| **5. Culture and Behavior** | Align organizational culture with governance goals; ethics and behavior |

---

## 7.3 COBIT Governance vs. Management Domains

| Governance Domains (E.D.M.) | Management Domains (P.B.R.M.) |
|---|---|
| **E**valuate | **P**lan (APO — Align, Plan, Organize) |
| **D**irect | **B**uild (BAI — Build, Acquire, Implement) |
| **M**onitor | **R**un (DSS — Deliver, Service, Support) |
| | **M**onitor (MEA — Monitor, Evaluate, Assess) |

---

## 7.4 COBIT vs. ITIL

| Aspect | COBIT | ITIL |
|---|---|---|
| **Focus** | IT **Governance** (what to do) | IT **Service Management** (how to do it) |
| **Scope** | Broader — enterprise governance of IT | Narrower — IT service delivery & operations |
| **Framework Type** | Control framework | Best practice guidance |
| **Primary Audience** | Board, executives, auditors | IT service managers, operations |
| **Complementary?** | Yes — COBIT for governance direction; ITIL for operational execution |

# SESSION 10: HIPAA OVERVIEW

---

## 8.1 HIPAA Overview

- **Health Insurance Portability and Accountability Act**
- Enacted in **1996** (USA)
- Protects healthcare information and ensures **data privacy**
- Applies to **Covered Entities**: healthcare providers, health plans, healthcare clearinghouses
- Also applies to **Business Associates** (vendors handling PHI)

---

## 8.2 HIPAA — 5 Titles

| Title | Focus |
|---|---|
| **Title I** | Health insurance coverage and portability (continuity of coverage) |
| **Title II** | Administrative simplification; national standards for electronic healthcare transactions; data privacy & security (most relevant for compliance) |
| **Title III** | Tax-related provisions; medical savings accounts |
| **Title IV** | Application and enforcement of group health plan requirements |
| **Title V** | Revenue offsets (tax provisions) |

---

## 8.3 HIPAA — 4 Rules (Critical for Exam)

| Rule | Purpose |
|---|---|
| **1. Privacy Rule** | Governs use and disclosure of **Protected Health Information (PHI)**. Sets patient rights over health data. |
| **2. Security Rule** | Establishes standards for securing **electronic PHI (ePHI)**. Covers administrative, physical, and technical safeguards. |
| **3. Breach Notification Rule** | Requires notification of affected individuals, HHS, and (sometimes) media in case of a data breach. |
| **4. Enforcement Rule** | Sets civil money penalties for non-compliance (tiered based on culpability). |

---

## 8.4 HIPAA Security Rule — 3 Safeguards

| Safeguard | Examples |
|---|---|
| **Administrative** | Risk analysis, security officer, training, contingency planning |
| **Physical** | Facility access controls, workstation security, device controls |
| **Technical** | Access controls, audit controls, integrity controls, transmission security |

---

## 8.5 Key Definitions

| Term | Definition |
|---|---|
| **PHI (Protected Health Information)** | Any health information that can identify an individual |
| **ePHI** | Electronic Protected Health Information |
| **Covered Entity (CE)** | Healthcare provider, plan, or clearinghouse |
| **Business Associate (BA)** | Vendor/subcontractor that handles PHI on behalf of a CE |
| **Minimum Necessary Rule** | Use/disclose only the minimum PHI needed |

# SESSION 11: PCI-DSS OVERVIEW

---

## 9.1 PCI-DSS Overview

- **Payment Card Industry Data Security Standard**
- Standard for securing **payment card transactions**
- Ensures protection of **cardholder data** during processing, storage, and transmission
- Applies to all entities that store, process, or transmit cardholder data

---

## 9.2 History

| Year | Milestone |
|---|---|
| **2004** | Developed by major credit card companies (Visa, MasterCard, Amex, Discover, JCB) — PCI Security Standards Council formed |
| **Multiple versions** | 1.0 → 2.0 → 3.0 → 3.2 → 3.2.1 |
| **2022** | **PCI-DSS v4.0** released (major update); v3.2.1 retired March 2024 |

---

## 9.3 PCI-DSS Merchant Levels

| Level | Criteria | Validation Requirement |
|---|---|---|
| **Level 1** | > 6 million transactions/year | Annual on-site assessment by QSA (Qualified Security Assessor) + quarterly network scan by ASV |
| **Level 2** | 1 – 6 million transactions/year | Annual Self-Assessment Questionnaire (SAQ) + quarterly scan |
| **Level 3** | 20,000 – 1 million e-commerce transactions/year | Annual SAQ + quarterly scan |
| **Level 4** | < 20,000 e-commerce transactions/year | Annual SAQ + quarterly scan (may vary by acquirer) |

---

## 9.4 PCI-DSS v4.0 — 12 Requirements (Grouped in 6 Goals)

| Goal | Req # | Requirement |
|---|---|---|
| **Build & Maintain Secure Network** | 1 | Install and maintain network security controls (firewalls) |
| | 2 | Apply secure configurations for all system components |
| **Protect Cardholder Data** | 3 | Protect stored account data (encryption) |
| | 4 | Encrypt transmission of cardholder data across open, public networks |
| **Maintain Vulnerability Management Program** | 5 | Protect systems and networks from malicious software (anti-malware) |
| | 6 | Develop and maintain secure systems and software (patch management) |
| **Implement Strong Access Control Measures** | 7 | Restrict access to cardholder data by business need-to-know |
| | 8 | Identify and authenticate access to system components (unique IDs, MFA) |
| | 9 | Restrict physical access to cardholder data |
| **Regularly Monitor & Test Networks** | 10 | Log and monitor all access to network resources and cardholder data |
| | 11 | Test security of systems and networks regularly (vulnerability scans, pen testing) |
| **Maintain Information Security Policy** | 12 | Maintain a policy that addresses information security for all personnel |

# SESSION 12: CIS CRITICAL SECURITY CONTROLS

---

## 10.1 CIS Overview

- **Centre for Internet Security** — nonprofit organization
- Provides **CIS Critical Security Controls (CIS Controls)** — a prioritized set of actions
- Focus: Identifying and mitigating the most prevalent security risks effectively

# SESSION 13: SSE-CMM PROJECT

---

## 11.1 SSE-CMM Overview

- **Systems Security Engineering Capability Maturity Model**
- Focuses on **security engineering processes** (not just IT, but systems engineering)
- Goal: Improve ability to develop, maintain, and assess **secure systems**

### Why it was needed:
- Increasing complexity of systems
- Security requirements becoming more demanding
- Existing process models lacked **security-specific practices**
- Standardize security engineering processes across organizations

---

## 11.2 History

| Period | Milestone |
|---|---|
| **1990s** | Developed to address security complexity in systems engineering |
| **Initial Release** | Introduced to create standardized processes for security engineering |
| **Adoption** | Used in government, defense, and critical infrastructure sectors |
| **ISO Adopted** | SSE-CMM became the basis for **ISO/IEC 21827** (Systems Security Engineering — CMM) |

---

## 11.3 Two Dimensions of SSE-CMM

### Dimension 1: Domain (Process Areas — WHAT)
- Practice areas addressing security:
  - Risk assessment
  - Threat analysis
  - Vulnerability assessment
  - Incident response
  - Security requirements
  - Security testing and verification

### Dimension 2: Capability Levels (HOW WELL)

| Level | Name | Description |
|---|---|---|
| **Level 0** | Not Performed | Process not implemented |
| **Level 1** | Performed Informally | Ad-hoc; depends on individuals |
| **Level 2** | Planned and Tracked | Process is planned, documented, and verified |
| **Level 3** | Well-Defined | Standardized process across organization |
| **Level 4** | Quantitatively Controlled | Measurable; statistical process control |
| **Level 5** | Continuously Optimizing | Process improvement based on metrics; adaptive |

## 12.2 Digital Personal Data Protection Act 2023 (India)

- Replaces outdated data privacy provisions from IT Act
- Regulates **processing of personal data** by organizations in India
- Establishes the **Data Protection Board of India**

### Key Principles:

| Principle | Description |
|---|---|
| **1. Lawful and Fair Processing** | Data may only be processed for lawful purposes with consent or **deemed consent** |
| **2. Purpose Limitation** | Data must be collected only for specified, clear purposes |
| **3. Data Minimization** | Only collect what is necessary for the stated purpose |
| **4. Accuracy** | Reasonable efforts to ensure data is accurate and complete |
| **5. Storage Limitation** | Data retained only as long as needed for the purpose |
| **6. Reasonable Safeguards** | Appropriate technical and organizational measures to prevent breach |
| **7. Accountability** | Data fiduciary is responsible for complying with the Act |

### Key Features:

| Feature | Detail |
|---|---|
| **Data Fiduciary** | Entity determining purpose and means of processing (like GDPR Controller) |
| **Data Processor** | Entity processing data on behalf of fiduciary |
| **Data Principal** | Individual to whom the data relates (like GDPR Data Subject) |
| **Consent Managers** | Registered entities managing consent for data principals |
| **Children's Data** | Special protections; verifiable parental consent for children under 18 |
| **Significant Data Fiduciary** | Higher compliance obligations for large-scale processors |
| **Cross-border Transfer** | Government may restrict transfers to certain countries via blacklisting |
| **Data Protection Board** | Enforces the Act; can impose penalties up to ₹250 crore |
| **Data Principals' Rights** | Access, correction, erasure, grievance redressal, nominate representative |

## Exam Tips — Key Differentiators to Remember

| Topic | Key Differentiator |
|---|---|
| **COBIT vs ITIL** | COBIT = Governance (WHAT); ITIL = Service Management (HOW) |
| **SOC 1 vs SOC 2** | SOC 1 = Financial controls; SOC 2 = Trust Services (Security, Availability, etc.) |
| **SOC Type I vs II** | Type I = Point in time; Type II = Over a period (operating effectiveness) |
| **SOX 302 vs 404** | 302 = CEO/CFO certification; 404 = Internal control assessment |
| **GDPR vs DPDP Act** | GDPR = EU (global reach); DPDP = India (consent-based) |
| **PHI vs PII** | PHI = Health-specific; PII = Broader personal identification |
| **SSE-CMM Dim 1 vs 2** | Dim 1 = WHAT (process areas); Dim 2 = HOW WELL (maturity levels) |
| **EAL 1 vs EAL 7** | EAL 1 = Basic testing (lowest); EAL 7 = Formal verification (highest) |
| **HIPAA Title I vs II** | Title I = Insurance portability; Title II = Data privacy & security |
| **CIS IG1 vs IG3** | IG1 = Basic hygiene; IG3 = Advanced/high-security environments |
| **PCI Level 1 vs 4** | Level 1 = >6M txns (on-site); Level 4 = <20K txns (SAQ) |
| **NIST Identify vs Protect** | Identify = Know your risks; Protect = Put safeguards in place |
